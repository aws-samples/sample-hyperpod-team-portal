## 1. 要解决的问题

平台使用**共享的 FSx for Lustre** 文件系统，按**一级目录（每个 team 一个目录）**划分使用空间：

```
<FSx 根>
├── team-a/     ← NLP 组
├── team-b/     ← 图像组
├── team-c/     ← 训练数据
└── team-d/     ← ...
```

平台可同时接入**多块** FSx（配置里逗号分隔 fs-id）。配额是**按盘独立**的：每块盘各自
一套一级目录 + 各自的容量上限，页面上先选盘再看/改该盘的目录配额。

当前问题：**没有存储配额**——任何一个 team 都可能写满整块 FSx，影响其他 team。需要：

1. **给每个一级目录设存储上限**（硬配额：超了写不进去，不是仅告警）。
2. **实时监控**各目录的用量 vs 配额，一眼看出谁快满了、谁超了。
3. 管理员能在平台界面上**直接创建目录并设置配额**，无需登服务器敲命令。

---

## 2. 方案概览

在**管理中心**新增「FSx 存储」页面，提供两块能力：

### 2.1 创建目录（一键，自动化）
管理员只填两项：**目录名** + **配额大小**。平台后端自动完成：
- 在 FSx 上创建该一级目录
- 分配 POSIX 组 ID（gid）+ 设置 setgid 权限（该 team 成员可读写、互不干扰）
- 打上 Lustre project 标签 + 设置存储硬配额

### 2.2 用量监控
以表格形式列出所有一级目录：目录名、gid、**已用/配额（进度条）**、状态（正常 / 接近上限 / 已超额）、文件数。近满和超额的目录用醒目颜色标出。

## 3. 底层技术机制

### 3.1 配额类型：Lustre Project Quota

FSx for Lustre（**2.15 版本**起）支持三种配额：user / group / **project**。本方案用 **project quota**：

- **按目录树限额**：给一个目录打上 project id，该目录及其所有子文件的总用量受这个 project 的配额限制。
- **硬限**：用量达到上限后，继续写入会被文件系统拒绝（`Disk quota exceeded`），从根本上防止写满。
- **实时统计**：Lustre 维护每个 project 的用量计数器（容量 + 文件数），读取是毫秒级，不需要遍历目录。

> 前提：project quota 需要**原生创建为 2.15** 的文件系统（本项目已就绪）。

### 3.2 执行载体：fsx-admin 管理 Pod

平台有一个常驻的 **fsx-admin Pod**，后端通过它执行 Lustre 命令来创建目录、设置和读取配额。

- **一个 Pod 挂多块盘**：每块 FSx 挂在自己的挂载点 `/fsx-mnt/<fs-id>`（一个挂载点只能对应
  一块文件系统，所以按 fs-id 分目录；用中性父目录 `/fsx-mnt`，不嵌在某块盘的根下以免污染该盘）。
  后端每次配额操作都带上目标文件系统 id，内部换成对应的挂载根。
- 该 Pod **不对外暴露**（无端口、无外部入口），只执行平台后端下发的固定命令。
- 设置配额需要 Linux `CAP_SYS_ADMIN` 能力（Lustre quota 系统调用的内核要求，无法用更小权限替代）。
- 开发机 / 训练任务挂 FSx **不经过**这个 Pod（各自独立的 PV/PVC），所以挂载点调整只影响配额管理。

### 3.3 权限与安全

| 项 | 说明 |
|---|---|
| **配额操作权限** | fsx-admin Pod 需 `CAP_SYS_ADMIN`（仅此一个 capability，非完整特权）。仅用于配额管理，Pod 无对外暴露、攻击面小。|
| **AWS IAM** | 配额是文件系统数据面操作，**不需要任何额外 AWS IAM 权限**。|
| **谁能操作** | 仅平台管理员（在管理中心页面操作）。|
| **配额对谁生效** | 各 team 的开发机 / 训练任务（以普通用户身份写数据）受配额硬限约束。|

## 附录 A：底层命令清单（技术参考）

以下命令由后端通过 fsx-admin Pod 执行，均已在真实环境验证。
下面 `<root>` = 目标盘在 fsx-admin Pod 里的挂载根 `/fsx-mnt/<fs-id>`。
gid 从 5001 起、project id 从 6001 起分配（分不同千位段，一眼区分两者）。

### 创建目录 + 设配额
```sh
# 例: 目录 team-e, 分配 gid=5005, project id=6005, 配额 100GiB
mkdir <root>/team-e
chown :5005 <root>/team-e               # group=5005
chmod 2770 <root>/team-e                # setgid + rwxrws--- (组读写, 新文件继承 gid)
lfs project -p 6005 -r -s <root>/team-e # 打 project 标签 (-r 递归, -s 继承)
lfs setquota -p 6005 -b 80G -B 100G <root>   # -b 软限(硬限80%) -B 硬限
```

### 查看用量（监控 / 刷新）
```sh
lfs quota -p 6005 <root>
# 输出 (~2ms, 不遍历目录):
#   Filesystem  kbytes   quota      limit       grace  files   quota  limit  grace
#   /fsx-mnt/fs-0aaa
#               977439   85899345   104857600   -      293     0      0      -
#   kbytes=已用KB  quota=软限KB  limit=硬限KB  files=文件数
# ⚠️ 挂载根路径较长时 lfs 会把 Filesystem 单独放一行、数值另起一行 (如上);
#    路径短时则同一行。解析要同时兼容两种排版, 否则用量会全读成 0。
#    超限的数值尾部会带一个 `*` 标记, 需剥离后再转数字。
```

### 修改配额
```sh
lfs setquota -p 6005 -b 160G -B 200G <root>   # 覆盖为 200GiB
```

### 删除目录 / 清配额
```sh
lfs setquota -p 6005 -b 0 -B 0 <root>   # 清配额 (0=无限)
lfs project -p 0 -r -s <root>/team-e    # 取消 project 标签
rm -rf <root>/team-e                    # 删目录 (仅 UI 删除操作 + 二次确认时执行)
```

### 辅助
```sh
ls -lan <root>                          # 列一级目录 + gid
lfs project -d <root>/team-e            # 查目录的 project id → "6005 P <root>/team-e"
lfs quota -t -p <root>                  # 查 project quota 的 grace period
```

## 附录 B：关键设计取舍

| 决策 | 结论 | 原因 |
|---|---|---|
| project quota vs group quota | **project quota** | 按目录树限额，更灵活，不强绑目录 gid |
| 硬配额 vs 软配额 | **硬配额** | 文件系统层强制，超了真的写不进去；软配额（仅告警）用户可绕过 |
| 数据源 | fsx-admin Pod 跑 `lfs` 命令 | Lustre 配额是数据面操作，不经 AWS API |
| 权限 | 仅 `CAP_SYS_ADMIN` | `quotactl` 内核硬性要求，已是最小权限（非完整特权）|
| 文件系统 | 原生 2.15 FSx | project quota 仅在原生 2.15 上可用。FSx 控制台**默认建 2.12**，在 2.12 上 `lfs setquota` 看着执行成功但配额不生效（`lfs quota` 返回 `Operation not supported` / 全 0），必须建盘时显式选 2.15 |
| 多盘挂载 | 一个 fsx-admin Pod 挂多块，`/fsx-mnt/<fs-id>` | 一个挂载点只能对应一块文件系统；共用一个 Pod 省资源，且配额操作都在同一处执行 |
| 盘的标识 | 配置里逗号分隔 `fs-id`，fs-id 做挂载点；界面展示走 AWS `Tags[Name]` | fs-id (`fs-<hex>`) 天然路径安全，直接当路径段，省去人工别名的校验/唯一性负担；展示名取 FSx 自身的 Name tag，无需二次维护 |
